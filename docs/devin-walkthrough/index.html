01 — The Problem

Security Vulnerabilities
Don't Wait for Your Sprint

Every open-source project faces the same challenge: security issues arrive unpredictably, demand immediate attention, and pull engineers off planned work. The question isn't whether vulnerabilities will appear — it's whether your response is manual or automated.

⚠

The Interrupt Problem

A critical CVE drops on Tuesday. An engineer stops feature work, context-switches to triage, traces the code path, writes a fix, adds tests, and opens a PR. That's half a day gone — best case.

⏱

The Response Gap

Average time to remediate a high-severity vulnerability is 60+ days across the industry (Veracode State of Software Security). Most teams don't lack the skill — they lack the bandwidth.

🔍

The Scaling Challenge

Superset has 500k+ lines across Python, TypeScript, Helm, and Docker. A full security audit requires expertise across every layer — and nobody has time to do it regularly.

What We Built

An event-driven security automation pipeline where GitHub Issues automatically trigger Devin — an autonomous AI software engineer — to triage, classify, fix, test, and open PRs for security vulnerabilities. No human intervention required between issue creation and fix delivery.

This is not a scanner. Scanners find problems. Devin finds problems, traces the code, assesses real-world severity, writes the fix with regression tests, and delivers a mergeable PR. The difference is end-to-end resolution.

Devin already has published automation templates for this pattern: Security Vulnerability Scan (weekly CVE scanning with auto-patch PRs) and OWASP Security Hardening (Top 10 audit with fix PRs). Our Superset implementation extends this pattern with event-driven triggering via GitHub Issues, rather than just scheduled scans.

Behind the Scenes: The Workflow

GitHub Actions Trigger

The workflow (.github/workflows/devin-security-review.yml) watches for two events:

on:
  issues:
    types: [opened, labeled]

# Trigger when:
# 1. Label "security-vulnerability" applied
# 2. New issue with "security" in title

Before dispatching, the workflow validates the issue (prevents duplicate sessions) and extracts context for Devin's prompt.

Devin API v1 Call

The workflow sends a structured prompt with full issue context:

curl -X POST \
  https://api.devin.ai/v1/sessions \
  -H "Authorization: Bearer ${API_KEY}" \
  -d '{ "prompt": "Security vulnerability
    reported... Classify, trace, fix,
    test, open PR." }'

v1 API Used instead of v3 because it works with Pro accounts — no ACU quota allocation needed. See API details →

What Devin Does (Autonomously)

Once the session starts, Devin operates with zero human input. Here's the 9-step process it follows, powered by Knowledge notes and a security-focused prompt:

1. Read & Understand

Reads the full issue body, classifies vulnerability type against OWASP Top 10

2. Search Codebase

Uses grep, AST analysis, and file reading to trace affected code paths from entry to impact

3. Assess Severity

Evaluates real exploitability, not just theoretical risk. May upgrade or downgrade the reported severity

4. Design Fix

Plans defense-in-depth approach: input validation, sanitization, secure defaults

5. Implement

Writes the code change, following existing conventions and patterns in the codebase

6. Write Tests

Adds regression tests that reproduce the original vulnerability and verify the fix

7. Run Checks

Executes pre-commit hooks, lint, type checks, and test suite

8. Open PR

Creates a PR with security advisory, OWASP classification, and fix explanation

9. Report Back

Comments on the original issue with findings, severity assessment, and PR link

The Vulnerability

XSS OWASP A03 CWE-79

SQL Lab rendered query results as live HTML by default. A crafted payload in query results:

SELECT '<img src=x onerror=alert(document.cookie)>'

would be rendered as a DOM element, creating a defense-in-depth gap.

The Fix

Merged PR #9

  • Flipped FilterableTable.allowHTML prop: true → false
  • Users who opted in retain preference via localStorage
  • Documented behavior change in UPDATING.md
  • 4 new regression tests for XSS payloads

The Vulnerability

CVE-2026-44307 OWASP A01 CWE-22

mako was pinned to 1.3.11. Version 1.3.12 patches a path traversal vulnerability: backslash characters in template URIs aren’t normalized on Windows, allowing a crafted URI like ..\..\..\windows\win.ini to escape the template root.

Blast radius: Read access to files outside the template directory on Windows-hosted Superset deployments. Reachable via Alembic migration scripts, engine-spec template paths, and any extension that loads Mako templates by URI.

The Fix

Merged PR #12
  • requirements/base.in: floor bumped to >=1.3.12,<2.0.0 + CVE annotation
  • requirements/base.txt: pinned to mako==1.3.12
  • requirements/development.txt: pinned to mako==1.3.12
  • pip-audit verified clean: 0 known vulnerabilities
  • Post-merge: Alembic template rendering + Superset boot validated
View PR #12 → View Issue #10 → Open Devin Session →

Reader note: This demo shows a different class of vulnerability — a dependency CVE rather than a code-level XSS. Devin’s approach adapts: instead of tracing code paths, it searched for all pinned references via grep, verified the fix version on PyPI, bumped 3 files, and ran pip-audit to confirm the CVE was resolved. The full audit trail is embedded in the PR description.

Key difference from Demo #1: Issue #7 (XSS) required code changes across 7 files (+82 lines, regression tests, config changes). Issue #10 (mako CVE) required dependency management across 3 files (+4 lines). Devin handled both autonomously, adapting its approach to the vulnerability type — from code-level defense-in-depth fixes to supply-chain version bumps with pip-audit verification.

05 — Why Devin

What an Autonomous Agent
Makes Possible

This system isn't just "AI-assisted" — it's autonomously operated. Here's what that enables that wouldn't be practical otherwise.

Zero-Interrupt Security Response

Traditional: engineer sees issue, context-switches, triages, fixes, opens PR. Minimum half a day.

With Devin: issue filed → PR delivered. No human interrupted. Engineers review the PR when convenient, like any other code review.

Full-Stack Audit at Scale

Devin spawned 8 parallel child sessions to audit Python, TypeScript, npm, Helm, and Docker simultaneously. One engineer would need days for this scope. Devin did it in one session.

Severity Judgment, Not Just Detection

A scanner would flag Issue #7 as "High" because XSS. Devin actually read the sanitizer code, verified the canonical payload doesn't execute, and correctly downgraded to Medium. That nuance matters for prioritization.

Compound Learning

Knowledge notes persist across sessions: OWASP classification rules, Superset-specific patterns, testing standards. Every session makes the next one better. Playbooks let anyone on the team trigger the same workflow.

Defense-in-Depth Gap

The Concept

Defense in depth means layering multiple independent security controls so that if one fails, others still protect the system. A defense-in-depth gap exists when you're relying on a single control — even if that control currently works.

In Issue #7’s Case

SQL Lab used js-xss (a sanitizer library) to strip dangerous attributes like onerror from HTML before rendering. The canonical attack payload <img src=x onerror=alert(...)> was already blocked by the sanitizer. So why fix it?

The gap: HTML rendering was on by default. The system relied entirely on js-xss to catch every possible attack vector. One library. One point of failure. If js-xss ever has a bypass (and sanitizer libraries regularly do), every SQL Lab user is immediately vulnerable.

How Severe Is This? Does It Actually Matter?

Low
Immediate exploitability

The canonical XSS payload doesn’t execute today. The js-xss sanitizer strips onerror attributes correctly.

Medium
Real-world risk

Even sanitized HTML causes outbound requests. An <img src="https://attacker.com/track"> tag loads and tracks users without triggering any XSS filter.

High
Future risk

Any future js-xss bypass instantly affects all SQL Lab users with HTML rendering on — which was everyone, by default.

Fix
Correct posture

Escape by default, opt-in to render. This is exactly what the fix does.

The Bottom Line

Yes, it matters. Not because the app is exploitable right now, but because security defaults should be safe. The previous default was “trust the sanitizer with everything.” The new default is “show plain text unless the user explicitly wants HTML.”

That’s the difference between hoping your lock is unpickable and also having a deadbolt.
